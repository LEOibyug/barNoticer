# 窗口、提示与动效专项验收 / 现代 macOS 视觉补充 Spec

日期：2026-10-08。

## 1. 结论与证据边界

**本轮结论：部分达标，暂不通过“更苹果、更现代”的整体验收。**

本报告承接 `docs/superpowers/specs/2026-10-07-project-refactor-design.md`。原 spec 的业务与数据约束保持；本报告细化窗口、提示、动效的视觉交付标准，冲突时以本报告的专项视觉要求为准。

验收对象是 `main` 上、基于 `12ce0a2` 的当前未提交重构文件，不把这些改动当作已发布版本。检查方法：源码审阅、现有安装版窗口截图/可访问性树观察、当前工作区 Debug 构建。

- 当前工作区 Debug 构建通过。日志：`/private/tmp/barNoticer-visual-audit-build.log`。
- 未对当前未提交版本运行整套回归测试，上一轮 225 项通过不能代替本轮结果。
- 当前运行进程来自 `/Applications/barNoticer.app`，PID 41425。实际主窗口仍包含内容区大标题、示例按钮、独立新分组栏；源码已改为系统工具栏，因此运行界面不等同于当前工作区。
- 观察到旧版主窗口为深色，新建面板仍为浅色，且时间计划菜单显示为“无…”；当前源码已去除强制浅色，不能把旧版错色直接记为新版缺陷。
- 新版浅/深色、动画实际观感、低透明度、高对比度、VoiceOver 均尚未完成实机验收。
- 没有修改实现、安装新版、改变提醒设置、创建/提交事项或发送模型请求。只增加本报告。

## 3. 阻塞项与具体整改要求

### V01 · P1：AI 窗口边界约束不完整

依据：`barNoticer/AIAssistantPanelController.swift:125` 的 resize 只限制尺寸；`:151` 的 center 把窗口底边放在可见区域高度的 62% 处，并未考虑窗口高度。`barNoticer/AIAssistantPanelView.swift:183` 仍固定内部宽度 720。

例：屏幕可见高度为 900 pt，恢复 520 pt 高度的审批窗口，底边为 558 pt，顶边即 1078 pt；即使尺寸不大于屏幕，位置仍越界。小宽度屏幕即使缩小 NSPanel，固定 720 pt 的内部视图仍可能被裁剪。

整改要求：

- 使用同一目标屏幕求理想位置，再将整个 frame 的四边限制在 visibleFrame 内，四周保留至少 12 pt。
- 首次显示、带历史结果重新打开、图片加入、审批展开、切换屏幕都重新执行边界约束。
- SwiftUI 根视图适应实际容器宽度；内容区有明确高度预算，长内容滚动，不裁切主操作。
- 最小可用尺寸与无可用屏幕时的回退有效，不产生负数宽高。

验收：在 900 pt 和 600 pt 可用高度下，恢复带图片和审批结果的聊天窗；关闭、发送、新对话、审批按钮均在屏幕内且可点击。

### V02 · P1：自定义动效没有系统辅助功能分支

依据：当前 NotchIslandController、ReminderPresenter、AIAssistantPanelController 和 SwiftUI 视图包含多处自定义动画，未发现 reduceMotion / accessibilityDisplayShouldReduceMotion 的处理。材质表面也未发现应用级降低透明度或增强对比度的明确处理。

整改要求：

- SwiftUI 与 AppKit/Core Animation 统一遵守当前系统偏好，运行中切换也生效。
- 减少动态效果开启：取消扩散、缩放、路径展开和弹性位移；使用立即切换或短淡入。不能只把 SwiftUI animation 设 nil，留下 CALayer 的动画。
- 降低透明度开启：让输入与正文使用稳定实色；先验证系统 material 自带适配，不额外重复造背景；自定义颜色叠层必须单独检查。
- 增强对比度开启：次要文案、分隔和焦点状态明确可读。原生语义颜色优先于降低透明度后的白字/灰字手调。

验收：三种系统偏好分别开/关，检查聊天、新建、岛展开、提醒；减少动态效果下无扩散/缩放，正文仍可读，业务触发与关闭回调正常。

### V03 · P2：提醒在展示内容前等待过久，光圈过于抢眼

依据：`barNoticer/ReminderSettings.swift:172` 定义预闪 2.15 秒、展开 0.72 秒、收起 0.56 秒；同文件定义 5 层 ring。`barNoticer/ReminderPresenter.swift:419` 使用黄色描边、阴影、线宽和缩放叠加。

判断：这是本产品的视觉判断，不声称违反 Apple 的固定时长规定。常驻轻工具收到一条普通提醒却先演示多层黄色光圈，信息到达慢，且普通信息被渲染得像警告。

整改要求：

- 默认普通提醒不使用五层黄色扩散圈；采用一次轻微边缘提亮，并与面板出现重叠进行，避免串联长预演。
- 事件到首段可读文字的设计目标为 500 ms 内（不含应用挂起/调度延迟）。关闭光效也不能关闭提醒本身。
- 普通回复使用中性视觉；警示色只用于逾期、失败等确实需要区分的状态。
- 进入/退出共享统一的动效语义，不混用明显不同的“弹跳、线性缩放、长路径揭幕”。
- 减少动态效果分支直接呈现内容，无光圈，无人为等待。
- 用户自定义的提醒停留时间继续保留；不能把光效时长算作用户阅读时间。

### V04 · P2：新建面板仍是固定尺寸，错误和复杂字段缺少空间

依据：`barNoticer/TodoCreationPanelController.swift:92` 为 640×300；`:149` 的 VStack 在日程、提醒、备注后增加错误 Label，但外层仍固定高度，无整体滚动和屏幕约束。TodoScheduleEditor 的 compact 布局采用单行排列。

整改要求：

- 内容按“任务内容 → 可选安排 → 提交”组织；标题获得一整行或至少主要横向空间，不与全部元数据同等争夺宽度。
- 简单任务保持紧凑；选择 DDL/周期后按需展开。错误出现时增加可用区域或让次要内容滚动，不能挤掉添加按钮。
- 新建使用紧凑编辑布局，详情使用表单布局；共享草稿不意味着所有控件必须横排。
- 保留完整的时间计划名称，最低宽度下“无时间”不截成“无…”。
- 保存错误持续可见，保留输入；不把错误变成短暂 toast。

验收：无时间、单次 DDL+提醒、多个时间点、自定义周期、保存错误分别检查；名称完整，无横向溢出，备注和添加均可达。

### V05 · P2：窗口阴影与裁剪机制尚未统一

依据：AI 和新建的 NSPanel.hasShadow=false，hosting layer 的 masksToBounds=true；视图又在根表面设置大半径 shadow。AI 还存在 AppKit 22 pt 与 SwiftUI 24 pt 的根圆角差异。

判断：外扩阴影存在被宿主裁剪的结构性风险，不能仅凭源码数值确认最终阴影表现。当前构建未运行视觉验证。

整改要求：

- 普通浮层使用系统窗口阴影或明确不被裁剪的外部阴影层，两者只选一个。
- 内容裁剪与外部阴影分工，根轮廓在 AppKit/SwiftUI 中一致。
- 岛允许专用深色附着形状，但不沿用普通浮层的大圆角模板。
- 不通过不断加粗描边弥补阴影丢失。

验收：浅/深背景、不同缩放显示器上边缘无切角、重影或矩形漏底；可从截图识别层级，但没有厚黑投影。

### V06 · P2：提示文案仍暴露实现细节，信息层级不一致

依据：`barNoticer/TodoRow.swift:375` 将保存失败 reason 拼入用户文案；新建也展示底层 localizedDescription。聊天和 AI 设置的清空确认同时展示多句流程解释。

整改要求：

- 提示第一句说明结果，第二句给出下一步。技术细节进入可展开“详细信息”或日志。
- 常规处理中状态保持内联；可恢复失败贴近输入；数据冲突/不可撤销操作使用原生 sheet/alert。
- 避免每个普通成功都弹窗；保留用户明确要求的后台 AI 回复弹窗。
- 错误和警告区别呈现，普通完成不采用黄色警报视觉。

示例文案见第 5 节。清空二次确认的行为和安全校验不可削弱。

### V07 · P2：新建窗口快速重开仍可能被旧关闭回调隐藏

依据：`barNoticer/TodoCreationPanelController.swift:37` 关闭动画完成后无条件 orderOut；show 不更新用于排除旧回调的代际状态。AI controller 已有 presentationGeneration，可作为行为参照。

整改要求：窗口响应使用“最近一次用户意图优先”。关闭动画期间重新打开时，旧 completion 不得再隐藏新窗口。减少动态效果分支也必须调用正确的最终状态处理。

验收：连续快速开/关/开，最终窗口保持可见、焦点可用，不闪退；此项属于交互质量，不能靠缩短动画掩盖。

## 4. “更苹果、更现代”的明确方向

### 4.1 层级而非装饰密度

推荐方向是“原生系统结构 + 克制的浮层材质 + 快速反馈 + 刘海专属黑色表面”。现代感由布局、反馈和连续性形成，不以玻璃数量、发光强度或圆角大小作为指标。

| 表面 | 应有表达 | 避免 |
|---|---|---|
| 主窗口 | 原生标题栏/工具栏、侧栏选中、清楚列表密度 | 在内容区再复制一套大工具栏 |
| 设置 | grouped Form、标签对齐、解释放 footer | 自制圆角卡片套表单再套卡片 |
| AI / 新建 | 一个统一浮层表面，输入为视觉焦点 | 每个字段一层厚描边、近黑卡片、彩色底板 |
| 岛 | 固定黑色附着外壳，内部用间距和字重分层 | 把每个分组渲染成独立发光窗口 |
| 提醒 | 单次轻提示，内容快速出现，主动作清楚 | 长时间预闪、普通回复使用黄色警报 |
| 错误 / 确认 | 系统 alert 或贴近输入的短说明 | 自画系统警告框、长篇技术解释 |

### 4.2 Liquid Glass 的适用范围

项目目标系统已是 macOS 26 系列，可优先评估系统提供的玻璃控件/容器，而不是用自制 blur+白色描边模拟。具体 API 可用性需在实现时查 SDK 确认，本报告不把“未调用某个 API”当作缺陷。

- 系统工具栏和标准按钮优先使用原生样式，让系统承担材质和交互变化。
- 若自定义浮层采用玻璃效果，只用于顶层操作容器或同组控件，内容阅读区保持稳定。
- 不把每张待办卡片玻璃化，不用高透明度牺牲正文对比度。
- 玻璃动效和普通 material 的选择以浅/深壁纸、窗口激活状态、降低透明度实测为准。
- 黑色刘海外壳保留，不为了全局玻璃化破坏与物理刘海的融合。

### 4.3 排版与交互

- 正文使用系统 body，区域标题 headline，辅助信息 caption；过长标题两行/详情可读，存储不截断。
- 字段周围以 8/12/16/24 pt 的间距节奏组织；具体数值为本项目设计起点，不是 Apple 官方规定。
- 一张表面通常只有一个显著主操作。取消/关闭低强调，危险操作独立使用 destructive role。
- 符号采用 SF Symbols 的一致尺寸、字重和渲染方式；不要同时堆满实心、彩色、多层次图标。
- 指针悬停有轻反馈，按下有清楚状态；键盘焦点同等清楚，不能仅靠 hover 暴露唯一操作。
- 窗口位置以当前交互屏幕为准；打开有稳定锚点，内容增加沿同一方向展开，关闭返回原来的入口关系。

## 5. 提示与文案系统

| 类别 | 位置/形式 | 示例 | 行为 |
|---|---|---|---|
| AI 工作中 | 输入行状态 + 小型 ProgressView | 查阅事项中… / 查阅记忆中… | 不阻塞隐藏；无伪造百分比 |
| 保存成功 | 原操作完成状态，通常不额外弹窗 | 已保存 | 仅在用户需要反馈时短暂展示 |
| 保存失败 | 对应表单内持久提示 | 未能保存。内容已保留，请重试。 | 明确重试；详细原因折叠或写日志 |
| 图片不支持 | 图片区旁内联提示 | 无法读取这张图片，请换一张。 | 文字和其他图片保留 |
| 同步编辑冲突 | 原生 alert/sheet | 这项任务已更新。 | 提供重新载入、保留修改/覆盖的明确选择 |
| 清空记忆 | 原生确认 alert | 清空全部记忆？ | 主文案：将删除 N 条记忆，无法恢复。待办和聊天记录会保留。取消/清空记忆 |
| 后台 AI 回复 | 岛式提示 | 回复摘要 + 继续对话 | 不抢焦点，返回现有会话 |
| DDL 提醒 | 岛式提示 | 任务标题 + 截止/剩余时间 | 完成、稍后或关闭保持现有语义 |

待确认清空在聊天中仍应明确“尚未清空”，不能让文案精简造成完成状态误导。审批开关不影响二次确认，这一点在设置说明中表达，确认框无需反复解释实现过程。

## 6. 动效节奏 Spec

下列范围为本项目起始建议，最终由实机录屏检查；不写成锁死数值的单元测试。

| 动作 | 建议节奏 | 动画内容 | 减少动态效果 |
|---|---|---|---|
| 悬停/按下 | 80–140 ms | 轻量颜色/不透明度变化 | 保留无位移反馈 |
| 普通浮层出现 | 160–220 ms | 淡入，可有极小位移 | 立即或短淡入 |
| 隐藏 | 120–180 ms | 淡出，焦点和最终状态及时处理 | 立即隐藏 |
| AI 结果区调整 | 180–240 ms | 高度连续变化；顶部/输入锚定 | 即时布局 |
| 岛展开 | 260–380 ms | 稳定轮廓展开，文字不缩放、不被拉伸 | 直接呈现 |
| 普通提醒 | 最迟 500 ms 内开始可读 | 单次边缘提示与出现重叠 | 无光效立即呈现 |
| 内容切换 | 120–180 ms | 轻淡变，不整窗跳动 | 即时替换 |

要求：

1. 自定义动画集中管理语义与辅助功能策略；不要求所有组件共享同一时长。
2. 用户再次触发时可中断或转向，不能排队播放旧动画。
3. 同一动作不叠加 SwiftUI、NSAnimationContext、CALayer 三套重复缩放。
4. 持续状态不用反复发光；只在状态变化时提供一次反馈。
5. 业务任务结束时状态立即切换，不能为等动画人为延迟模型回复、保存成功或提醒。

## 7. 必须补齐的视觉证据

| 验收项 | 最低证据 | 当前状态 |
|---|---|---|
| 新版与工作区一致 | 构建路径、构建时间、源码快照/提交标识对应 | 构建通过；运行版不一致 |
| 主窗口与设置 | 浅/深各一组，同尺寸截图 | 新版未验收 |
| AI 面板 | 空闲、工作中、长回复、多审批、图片+错误 | 源码审阅；新版未验收 |
| 新建面板 | 所有日程类型及保存错误 | 旧版空闲观察；新版未验收 |
| 窗口尺寸 | 900/600 pt 可用高度恢复审批、窄屏、换屏 | 发现源码边界问题 |
| 提醒特效 | 普通提醒/后台回复短录屏，标明内容首次出现时间 | 未录制；代码仍为旧时序 |
| 系统辅助功能 | 减少动态效果、降低透明度、增强对比度各一次 | 源码缺少完整策略，未实机验收 |
| 交互 | 快速开关、Tab/Shift-Tab、Esc、中文候选确认 | 新版未验收 |

录屏用于判断动作连续性，单张截图不能证明动效好坏。演示使用临时测试数据，不把用户真实待办、记忆、接口配置写入验收素材。

## 8. 再次验收的通过条件

- V01、V02 的完整行为约束满足。
- V03–V07 各有整改和相应场景证据，不只是修改样式常量。
- 当前重构版本的关键回归测试通过；源码与运行包一致。
- 系统控件、内容层级、浮层、提示与动效遵守同一套设计；无需追求“全局玻璃”。
- 交付明确哪些项目已实测，哪些仍未验证；不以 build succeeded 或测试数量代替视觉结论。

本轮仅交付验收意见与补充设计。未来实现不应因这份报告删除现有未提交工作，应该在现有重构上修正并保留可追踪 diff。
