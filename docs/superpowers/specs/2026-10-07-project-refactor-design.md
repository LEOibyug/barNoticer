## 1. 目标与成功标准

barNoticer 是常驻的轻量待办工具，主入口是刘海区域，主窗口承担完整管理，AI 面板承担快速输入与执行。重构应围绕响应速度、安静运行和信息清晰度展开。

三个目标：

1. 减少重复计算、重复业务逻辑及无意义唤醒；业务规则集中，窗口不承载请求生命周期。
2. 减少测试维护成本和执行等待，保留对真实故障有发现能力的测试。
3. 建立一致的 macOS 信息层级、语义颜色、系统控件和键盘交互，同时保留刘海岛的辨识度。

验收结果必须同时满足：现有关键场景无回归；无存储迁移；指定冗余路径被消除；浅色、深色与可访问性检查通过；提供前后测量数据。代码行数和测试个数不作为单独的完成指标。

## 2. 不变条件与非目标

### 2.1 必须保持的用户体验

- 图片和文字可单独或混合输入；原有 4 张、单图 20 MB、长边 2048 像素的限制保持。
- 隐藏聊天窗、Esc、点击其他窗口不会取消模型请求。再次调起继续本次应用运行内的会话。
- 新对话是显式操作，取消旧请求但不撤销已执行事项；不引入跨重启聊天恢复。
- 后台回复继续通过提醒样式窗口呈现，不抢焦点；提醒和回复按现有队列规则展示。
- 开关 AI 主动提醒不影响用户设置的 DDL 提前提醒。定时提醒到点不等待 AI。
- 全局记忆按需查阅；原始查阅结果不进入后续轮次历史；重复查阅替换旧结果。
- 用户当前要求和明确保存的定义维持既有优先级；清空记忆无论审批开关如何均须二次确认。
- 岛内不显示创建时间。按重要性分组时显示任务所属自定义分类；按自定义分类分组时不重复显示分类名。
- 标题承载动作、对象和必要区分信息；细节放备注，不通过截断存储标题解决视觉拥挤。
- 默认分组、排序、拖动分组、重复事项推进、备注、全局快捷键及开机自启保持可用。

### 2.2 技术约束

保持 SwiftUI/AppKit/SwiftData，保持现有最低系统版本、UserDefaults key、模型字段、记忆格式和 AI 工具协议。后台提醒依旧只有规定的读取能力。不增加第三方运行时依赖。

本轮不做云同步、SwiftData 架构迁移、模型接口迁移、所有模块的抽象重写、公开签名/公证，也不改造为完整聊天客户端。

## 4. 架构选择和模块边界

### 4.1 采用渐进式职责收敛

不选择全量重写：当前后台会话、提醒和记忆已有大量回归约束，替换全部对象会扩大验证面。也不只换外观：日程重复及数据丢失风险需要先解决。

继续由 AppDelegate 创建并长生命周期持有服务。保留以下边界：

| 模块 | 拥有的状态/职责 | 不应拥有 |
|---|---|---|
| TodoScheduleDraft（拟新增） | 日程编辑值、原始值、变更字段、校验与变更描述 | NSWindow、网络、数据库提交 |
| TodoScheduleEditor（拟新增） | 显示日程类型/日期/周期/提前提醒，绑定草稿 | 自己复制业务规则或直接保存模型 |
| 事项查询与摘要 helper（拟新增） | 按 ID 查找、批量摘要、已删除/读取失败结果 | 对视图透明的全局模型缓存 |
| AIAssistantModel（保留） | 会话、请求任务、工具循环、审批、取消、完成事件 | AppKit 文件选择窗口细节 |
| AIAssistantPanelController（保留） | 窗口显示、隐藏、焦点、尺寸、完成事件转呈现 | 因隐藏窗口取消请求 |
| ReminderScheduler（保留） | AI 主动判断与自动 DDL 判断的启停 | 用户主动定时提醒的启停决定 |
| ScheduledReminderScheduler（保留） | 主动定时提醒、下次唤醒、文案缓存 | 等待模型后才决定是否按时提醒 |
| ReminderPresenter（保留/内部拆分） | 面板队列、闪烁、通知渠道、展示生命周期 | 决定用户定时提醒是否成立 |
| SettingsPage / SettingsSection（拟新增） | 设置容器与系统分组样式 | 存储、网络、额外状态副本 |

优先共享数据和规则，允许新建与编辑采用不同布局。仅有一个调用点的直通 helper 不为“架构完整”单独成层。文件拆分按职责，不以固定行数为目标。

### 4.2 AI 整理限度

AIAssistantModel 同时处理图片输入和工具循环，但不能贸然把一次请求拆成多套状态机。优先移出共享事项摘要查询、图片选择桥接；是否再拆请求执行器取决于能否只保留一个取消源、一个会话代际标识和一个操作成功记录。

保留 `hasAppliedActions` 的错误语义：已写入操作后网络失败不得恢复成可重复提交的原始草稿；已有待确认操作也不应丢失。记忆 epoch、revision、强制确认标识必须继续参与原来的检查点。

## 5. 日程与事项数据设计

### 5.1 草稿内容与生命周期

草稿包含：日程类型、单次 DDL、全部多时间点数组、重复规则、重复起点、提前提醒分钟数，以及编辑时的原始有效值。新建默认无时间；切换类型可以保留临时输入，但只提交当前类型的有效字段。

1. 打开编辑器时从模型创建一次草稿；所有时间点完整载入，按时间顺序展示。
2. 控件只修改草稿。通过有效字段差异判定是否变更，不再给每个 setter 手写 scheduleWasEdited。
3. 提交前读取当前模型；任务已删除时给出明确反馈，不重建它。
4. 未变更字段不写回。用户只改提醒时间时，不改日程和重复推进记录。
5. 修改一个多时间点不得重建为两个时间点。已有一项、三项或更多项均可编辑和完整保存；本轮不增加任意新增/删除时间点的全新产品能力。
6. 提交成功后刷新草稿基线；失败保留输入和错误，不假装完成。

关闭设置时自动提交的既有语义保持；“完成”和关闭回调不能造成重复的有副作用写入。关闭过程的异步动画不是提交成功信号。

### 5.2 合并和冲突规则

用户编辑过程中，AI 或另一窗口可能修改同一事项。用原始值、当前值、草稿值做字段级比较：只应用用户实际编辑的字段，保留其他外部变化；同一有效字段同时被两方修改且结果不同，则保留草稿并提示“事项已更新”，提供重新载入或明确覆盖选择。updatedAt 可作提示信号，但不能作为唯一的冲突判断，因为无关字段也会改变它。

日程类型和该类型有效字段作为一个整体合并，避免把旧截止时间和新重复规则混在一起。重复规则改变时对 lastCompletedOccurrenceAt 的处理仍遵循既有模型语义；本轮不顺带重新定义重复完成算法。

### 5.3 保存失败

显式提交必须区分“已修改内存”和“已持久化”。新建失败保持窗口、标题和备注；重试不能插入多个相同草稿对象。编辑失败保留待保存提示和重试入口。

禁止对共享 ModelContext 无条件 rollback：它可能撤销其他窗口或 AI 的修改。采用限定到本次操作的恢复，或仅在证明不会丢失并发变化后使用独立提交上下文。错误信息采用短中文说明；底层详细错误进日志。

验收：四种日程类型、新建/编辑一致；未编辑直接关闭不改变 updatedAt、提醒投递标记或重复完成记录；4 个时间点修改第 1 个后其余 3 个完整保留；DDL 转其他类型清除不适用的提前提醒；提交失败可以原样重试。

## 6. 查询、排序与刷新

### 6.1 排序

每次排序构造一次分组索引；每个事项只计算一次 nextOccurrence。比较键的顺序必须保持：未完成优先 → 分组顺序 → 逾期/24 小时内/更远/无时间 → 具体时间 → 重要性 → 创建时间。

不同入口现有语义须分别保持：重要性视图不意外继承自定义分组顺序；自定义分组视图遵循持久化分组排序。未知或已删除分组继续归默认分组。

分组数据先规范化一次；排序结果按分组分桶，不再每个分组从头全量筛选。岛先过滤未完成再排序。同次渲染优先使用一个派生结果，避免多个 computed property 独立重复计算。不引入跨更新长期缓存，除非具有可靠失效机制。

### 6.2 单项读取与回复卡片

单项查询使用 ID predicate 和 fetchLimit；多卡片渲染优先按所需 ID 批量取回，分组索引共享一次。AI 回复和提醒共用同一摘要构造规则，但不强迫两个界面共享所有外观。

区分事项不存在、已完成、读取失败。读取失败不要显示成“事项不存在”。后台取消、删除或完成后的卡片刷新仍通过现有通知/模型观察途径更新。

### 6.3 视觉时间刷新

岛关闭时可停止相对时间 UI 的每分钟刷新，重新显示时立即更新。不要将 UI 刷新计时器与业务提醒计时器合并。需验证隐藏窗口的 SwiftUI 生命周期；不能假定 orderOut 会调用 onDisappear。

## 7. 提醒调度设计

### 7.1 事件驱动与单个下次计时器

ScheduledReminderScheduler 保留一个可取消的 one-shot timer，正常时指向最近一次未投递提醒。没有待提醒事项且没有重试时不装 timer。

重算来源：首次 start、事项保存、提醒设置变化、记忆变更、系统唤醒、系统时钟变化。时区变化若影响本地日期解释或文案，应更新文案和展示；已存绝对 DDL 的 fireDate 不因时区变化被重新解释。

保存通知覆盖必须先验证：主窗口、岛、编辑器、AI、拖动、完成、删除、自动保存都要触发正确重算。若某入口只改内存并依赖延迟 autosave，应补明确提交/数据变化事件后再删除 30 秒兜底，不能直接移除轮询。

通知合并为一次待执行 refresh，避免批量操作和投递标记保存引发重入或不断重装 timer。start 幂等；停止/释放后所有 observer、timer、文案 Task 被回收。

### 7.2 投递与重试

到期事项先验证当前是否仍未完成、配置是否仍匹配，再沿用现有“标记保存成功后呈现”的顺序。数据库读取或标记保存失败保留可重试状态；第一次失败 30 秒后重试，连续失败使用有上限的退避（建议 30/60/120/300 秒），新数据事件可提前重试。

到点优先本地文案，绝不等待网络。AI 文案必须匹配本次事项内容、DDL、提前分钟数、提醒风格和记忆 revision；标题、备注、时间、风格或记忆改变后不能使用旧结果。当前生成请求失效时应取消或在完成时丢弃，再为最新内容准备。

不能宣称端到端 exactly-once：本地标记落盘和通知/窗口展示无法组成同一事务，进程在两者之间崩溃可能漏展示。本轮保持现有去重策略，验收覆盖常规重启和重复回调；若要可恢复投递队列，另立存储设计。

### 7.3 AI 主动提醒

aiPollingEnabled 为 false 时，AI 轮询 timer 和默认 DDL 扫描 timer 均不存在，ScheduledReminderScheduler 继续运行。开关变化即时重装/移除对应 timer；已在途的 AI 判断结束后再次检查开关，不弹出过时提醒。

避免改用一个统一轮询器，因为用户主动定时提醒和可选 AI 判断具有不同准确性及权限要求。

### 7.4 指针轮询单独评估

0.12 秒的指针轮询不在“发现 timer 就删除”的范围。先记录其在空闲、全屏、切换 Space、外接屏和岛动画过程中的作用。优先方案是停留/进出事件加有限恢复检查；若没有等价稳定性证据，保留现有轮询，只减少回调内重复坐标与布局计算。

## 8. macOS 原生视觉规范

### 8.1 视觉语言

- 主窗口、设置、AI 与新建面板使用语义颜色，跟随系统浅色/深色；刘海岛与岛式提醒固定深色。
- 优先系统字体层级 body、headline、caption，正文和次要信息分开；不依靠大量低透明度白字表达层级。
- 主要信息只有一层承载表面。弹窗可用 regularMaterial；内部区域以间距和分隔线分组，避免每层都叠加圆角、填充和描边。
- 间距以 4/8/12/16/24 pt 为设计参考，内嵌控件遵循系统尺寸。圆角统一由组件语义决定，不为所有区域采用同一个大圆角。
- 采用一个窗口阴影来源，避免 AppKit 阴影与 SwiftUI 厚重阴影叠加或因裁剪导致阴影失效。
- 系统强调色用于主操作与选中；优先级色保留但不填满整张卡片。辅助功能标签仍读出重要性，不能只传递颜色。

### 8.2 主窗口

结构：原生 NavigationSplitView；侧栏保留“待办 / 分组 / 偏好”，详情区由系统工具栏、可选分组编辑区和列表组成。

- List(selection:) 或等价原生选择路径取代自画选中底色。支持键盘上下移动、焦点环和 VoiceOver。
- 标题放 navigationTitle；副标题反映当前列表数量。已完成页不得显示“正在进行”的数量。
- “新建事项”和“新建分组”进入工具栏。“新建分组”打开小 popover，包含名称输入和确认按钮；Enter 提交，Esc 关闭，焦点进入名称框。
- 删除空操作 onChange。示例数据入口只在无事项时显示于空状态；不占常驻主工具栏。
- 保留分组拖动 handle、拖动预览、目标提示与持久化顺序。原生选择与拖动不能互相抢手势。
- 当前分组的改名、颜色、删除使用紧凑编辑区或管理 popover。默认分组限制保持，删除后事项回默认分组。
- 颜色菜单展示中文色名/色点，hex 仅留在数据层，不作为主要用户文案。
- 事项行：左完成按钮，中标题及次要元数据，右详情按钮。标题长时视觉截断并可查看完整内容，存储文本不截断。
- 本轮只保持岛不显示创建时间；主列表是否隐藏创建时间不擅自扩展用户需求。

布局验收：现有默认 760×520 主窗口下可用；扩大窗口后内容不挤在左上角；较长中文分组、标题、日期不遮挡操作。

### 8.3 设置页

四页共用 SettingsPage + 原生 grouped Form + SettingsSection。各页保留业务 State 和已有存储逻辑，不让通用布局容器持有配置。

- 页名只出现一次；说明文字放 Section footer，不给每张自制卡片堆标题和副标题。
- AI 页：接口、交互、全局记忆、连接测试。URL 和模型字段有稳定标签；Key 保持隐藏。
- 提醒页：先任务定时提醒，再 AI 主动提醒，再呈现/布局。清楚说明关闭 AI 不关闭主动定时提醒；关闭后仅禁用相关轮询选项，提醒风格如被定时文案共用则保持可编辑。
- 岛页：模式、热区、展开区域。修正文案中“宽体必定按重要性三列”的描述，因为用户也可按自定义分类。
- 应用页：新建快捷键、启动；调试日志入口移入应用页的高级分组，避免与岛外观混在一起。
- 自动保存保留。滑块数值用系统等宽数字；支持键盘操作。预览结束须移除临时边界和预览面板。
- 全局记忆保留列表、来源、数量和清空入口；较长内容可滚动。保留现有强制确认 alert，UI 简化不得改变 token/revision 校验。

### 8.4 AI 面板

保留 Spotlight 式中心输入：顶部轻量会话操作、主输入行、图片预览、结果/待确认区。新对话与隐藏始终是两个含义明确的动作。

- 系统材质承载整个面板；输入区不再用近黑色厚卡片套一层，发送按钮用强调色表达可用状态。
- AppKit NSTextField、NSTextView、插入光标、placeholder 与 SwiftUI 同步采用语义色；不能只移除 darkAqua 而保留白字。
- 查阅事项、查阅记忆、记录记忆等活动继续显示在输入框内；活动结束恢复输入。中文 marked text 不受状态刷新或外观切换破坏。
- 长回复滚动，文字可选择；多条待确认操作必须有独立受限滚动区，底部操作可达。图片+长回复+批量操作不能撑出屏幕。
- 面板理想宽度可沿用 720 pt，但外层尺寸必须夹在当前屏幕 visibleFrame 内；不是对所有屏幕硬编码同一高度。
- 事项卡片统一摘要信息；在浅色下选用能读清的优先级色，不复用仅适合黑底的 islandColor。
- 系统“降低透明度”时采用实色背景；提高对比度时边界可见；“减少动态效果”时去除大幅缩放和位移。

### 8.5 新建与编辑

新建面板保持快速输入优先，不为共享表单而把简单创建变成大设置窗。无时间时显示标题、重要性、分组、可选备注和添加；选择日程后展开对应字段，按内容计算高度并限制在屏幕可用高度内，超出部分滚动。

新建和事项详情共享日程规则及字段控件，布局可以不同。Enter 的现有标题提交和 Cmd+Enter 行为保留，中文候选确认不能触发创建。

删除强制 aqua，文本背景使用系统色。错误在相关区域以短说明呈现，不消失、不自动关闭；按钮可再次重试。

### 8.6 岛与提醒

岛黑色外壳保持，简化内部分组框和彩色描边。标题、数量、操作入口有明确层级；可以移除头部“第一项重要性”徽章，因为它不代表整个列表。重要性由分组标题、细色条/色点传递。

按重要性展示：每项可见其自定义分类名。按自定义分类展示：分类名仅在分组头部出现。两种模式均不显示任务创建时间。

提醒复用岛的文字层级与轻量卡片规范。相关事项和继续对话操作可达；关闭、自动收起、打开聊天不改变业务请求状态。不能为视觉统一删除呈现队列、旧回调代际检查或焦点保护。

## 9. 测试精简策略

### 9.1 筛选规则

删除测试的理由必须能明确指出：只重复实现常量、验证无行为的包装、或与另一个实际行为测试完全重叠。短测试不等于无价值；小状态机、窗口焦点、数据边界应保留。不得为了减少总数合并所有风险点成一个庞大测试。

TDD 精简为：行为变化和真实缺陷补最小失败用例；已有行为下的内部重构复用现有测试；视觉常量不新增单元测试，以实际渲染检查替代。

### 9.3 测试设施

统一创建仅内存 ModelContainer 的 helper；重启持久化验证仍使用临时磁盘库，不能全部替换成内存库。UserDefaults suite 每 fixture 独立、结束清理；日志不写真实用户目录。

HTTP 公共部分只包括 body/httpBodyStream 读取、响应构造、可控制完成和取消。不同 fixture 的返回内容与失败顺序留在具体测试。共享设施必须有按请求或 fixture 隔离的状态，不以单一 static 队列作为全套测试共用调度器。

异步测试用明确事件/expectation 控制“请求已发出/允许返回”，减少 5 ms 忙轮询和固定 sleep；窗口动画仍保留少量集成验证，其余状态逻辑使用受控时间。timeout 是失败上限，不是必等时长。

保留先串行运行的基线；只有 fixture 隔离证明成立后才考虑并行测试。不能用“开并行”掩盖慢等待或共享状态。

### 9.4 本轮应补的最小行为用例

- 编辑三项以上时间点后没有丢失未编辑项。
- 未修改日程直接关闭不写回、不改变重复完成进度或投递标记。
- 同一字段并发修改提示冲突，无关字段修改保留。
- 保存失败保留草稿；重试没有重复插入，且不撤销其他待保存变化。
- 无有效定时提醒时不调度周期性扫描；新增/提前/删除/完成事项即时重算。
- 保存投递标记失败后仍可重试；唤醒和时钟变化重新判断到期。
- AI 主动开关关闭后对应 timer 不唤醒，用户定时提醒仍投递。
- 排序和分组重构保持原有顺序、未知分组回退及全部事项可达。

不为每个新增 helper、枚举映射或样式参数配一份形式上的测试。

## 10. 验收矩阵与测量

### 10.1 功能验收

| 场景 | 预期 |
|---|---|
| 发图文 → 隐藏 → 后台执行 → 再唤起 | 会话/结果/待确认操作保留，后台弹窗不抢焦点 |
| 新对话时旧网络回调迟到 | 不覆盖新会话，不重复执行旧操作 |
| 清空记忆：审批开/关、全部执行、设置入口 | 都二次确认；取消无副作用；旧 token 无效 |
| AI 读取记忆后下一轮对话 | 原始记忆工具结果不继承，状态文案正常 |
| AI 关闭、网络失败、文案未生成时 DDL 到点 | 本地提醒正常；同一 occurrence 去重 |
| 休眠错过提醒后唤醒、修改系统时间 | 重新计算并补发，未完成有效提醒不静默漏掉 |
| 4 个时间点事项只编辑一个 | 其余时间保留，排序稳定 |
| 完成重复事项 | 推进当前周期，未变成永久完成 |
| 分组排序/删除/默认分组 | 主窗口和两种岛模式一致，孤立事项归默认组 |
| 浅/深色下中文输入、截图粘贴、Enter | 文字光标可见，候选不被覆盖、未完成输入不提交 |

### 10.2 视觉验收

至少检查主窗口有数据/空状态、4 页设置、AI 空闲/处理/长回复/多审批、图片+错误、新建各日程类型、事项详情多时间点、窄岛/宽岛两种分组、提醒与后台回复。

浅色/深色、长中文与英文、默认 760×520 主窗口、缩小可用屏幕、增加对比度、降低透明度、减少动态效果均需检查。完成按钮、提交、清空确认必须通过键盘和 VoiceOver 可达；无文本重叠、裁剪或不可滚动尾项。截图不包含真实 API Key、用户记忆或私密事项，使用临时测试数据。

### 10.3 性能测量方案

固定同一台机器、同一电源状态与 Release 配置；使用相同临时数据：空库、100 项/10 组、1000 项/20 组，包含无时间、单次、多点和重复事项。冷启动与预热后分别记录。

- 排序/分组：预热后至少 30 次，报告中位数和 p95；通过 profiler 确认比较器不再触发重复日程解码。目标是不劣于基线，收益幅度由实测报告。
- 空闲 5 分钟：AI 关闭、无定时提醒、岛隐藏时记录 CPU、wakeups、数据库扫描次数；调度器自身不产生周期扫描，指针轮询单独归因，不能宣称整个应用零唤醒。
- 界面：岛展开、分组切换、AI 显示和 4 张接近输入上限的图片导入，观察主线程超过 100 ms 的连续阻塞。若图片造成阻塞，再落实异步导入，并加入会话变更时丢弃旧导入结果的检查。
- 提醒：应用清醒且调度线程正常时，到点触发不得被网络延迟影响；报告 timer 触发与可见弹窗延时，后者包含既定闪烁动画，不混为时间误差。
- 测试耗时：同一环境至少 3 次，记录总耗时和最慢测试。基线本次测试执行约 145 秒，仅作参考，不承诺按删测试个数同比下降。

## 12. 明确延期项
